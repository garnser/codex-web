# Canonical Decisions and Bounded Deliberation\n\nCodex-web stores important decisions as durable canonical records rather than reconstructing them from chat history. Decision reasoning is advisory; authority and side effects remain outside the Decision domain.\n\n## Canonical record\n\nA Decision records the question, initiator, explicit participants, exact evidence references, assumptions, constraints, options, risks/pros/cons, bounded reasoning budget, recommendation, dissent, approval binding, final decision, review/expiry dates, supersession, revision history and post-execution reviews.\n\nStates are `draft`, `analysis`, `awaiting_approval`, `approved`, `rejected`, and `superseded`. Content revisions are allowed only before canonical approval is requested. Requesting approval freezes one exact Decision revision and digest.\n\n## Evidence and metrics\n\nCanonical Evidence references resolve to live valid Evidence records when attached. Metric-backed evidence must reference an immutable `MetricSnapshot` from the M8 metric domain. The Decision copies the snapshot's metric revision, freshness state, aggregate value/unit, contributing observation IDs and exact window into its evidence reference.\n\n`stale`, `missing`, and `partial` metric states remain explicit. They are not promoted to fresh fact by the Decision or by model synthesis. Missing snapshot IDs fail closed.\n\n## Bounded deliberation\n\nModel-assisted deliberation is optional and bounded. One round performs one analysis invocation for each explicitly configured participant in parallel, followed by exactly one synthesis invocation. Participant count, round count, input tokens, output tokens, model calls and model cost are hard limits stored on the Decision.\n\nEvery model invocation carries `decision_id` attribution through the Model Gateway. Known state, budgets, approval state and evidence provenance are determined by code, not by model output. Model output is schema validated and cannot approve a Decision or create Work/ActionIntent side effects.\n\n## Approval boundary\n\nDecision approval reuses the canonical ApprovalRequest domain. The request is bound to `operation=decision.approve`, the exact Decision ID, revision and deterministic content digest.\n\nWhen quorum is satisfied, finalization consumes the ApprovalRequest and changes the Decision from `awaiting_approval` to `approved` atomically through the shared SQLite document transaction. Rejection/expiry/cancellation/invalidation map to a durable rejected Decision state. There is no Decision-local vote or approver lifecycle.\n\n## Side effects\n\nAn approved Decision is a record of authority and reasoning, not an execution mechanism. External changes must still pass through canonical Work and/or ActionIntent/ActionProvider paths. Post-execution reviews may reference canonical Work/ActionIntent and Evidence records but do not directly invoke providers.\n\n## UI\n\nThe Decision workspace reads the same canonical API. It exposes exact metric/evidence provenance, participant analyses, synthesis invocation IDs, token/cost usage, recommendation, dissent, ApprovalRequest target/revision/digest, final decision, and revision/event history. It does not calculate a parallel client-side decision state.\n
## Goal-to-Decision-to-Work traceability

A Decision may bind to one canonical Goal through `goal_id`. The Goal is resolved in the same tenant/workspace when the Decision is created or revised; an arbitrary or cross-tenant identifier is rejected.

Approved Decision consequences are materialized only through the existing authoritative-task ActionProvider and durable ActionIntent path. A work specification is preflighted before any external task is created. Each ActionIntent carries both `goal_id` and `decision_id`; after a successful provider receipt is reconciled to a canonical Work Item, codex-web binds `goal_id`, `decision_id`, and `originating_action_intent_id` onto that Work Item. Existing conflicting provenance fails closed.

Decision work specifications and their ActionIntent/Work Item reconciliation state are durable on the Decision. Stable per-Decision/per-item idempotency keys make retries reuse the original ActionIntent. Independent approved consequences may be appended later without redefining prior work.

Parent/blocking relationships are created through the canonical WorkGraph service after all referenced Work Items exist. When the Decision is Goal-linked, generated root Work Items are added to the Goal's canonical work-graph bindings so deterministic Goal progress/completion includes the Decision-generated work.

The Decision trace endpoint joins the canonical Goal snapshot, Decision record, Work Items, ActionIntent histories/receipts, and post-execution reviews. It does not copy provider payloads into a second trace store. The workspace reads this endpoint to show the `Goal -> Decision -> Work -> Result` chain.

Canonical Evidence and MetricSnapshot references in the Decision workspace link to their canonical read APIs. The UI does not synthesize duplicate evidence records.
